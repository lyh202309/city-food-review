# 秒杀券下单与库存扣减优化

## 原有实现方案：Redis Lua 预扣 \+ RabbitMQ 异步落库

```Markdown
① Redis Lua 抗并发（预扣库存 + 一人一单Set去重）
        ↓
② 发消息到RabbitMQ 
        ↓
③消费者落库（一个事务内两道防线）
   ├─ ① 扣 DB 库存：UPDATE ... WHERE stock > 0（乐观锁）
   │     失败 = 超卖 → 回滚 Redis + 告警
   ├─ ② 建订单：save(voucher_order)
   │     
   └─ 成功 → ack → SSE 通知前端（订单=待支付）
```

### 但是原有实现方案使用RabbitMQ上并没有考虑以下问题：



1. 扣减库存成功后，消息队列宕机了怎么办?下方\(一\)解决

2. 扣减库存成功后，消息队列的消息丢了怎么办?下方\(一\)解决

3. 开启消费者确认机制之后，消息队列既没有回复ack也没有回复nack咋办？下方\(一\)解决

4. 扣减库存成功后，消息队列没有宕机，但消息延迟了怎么办?下方\(一\)解决

5. 消息落库失败重试造成的多次操作的幂等性怎么保证？下方\(二\)解决

6. 订单没有延迟，但修改余票和座位状态失败了怎么办?下方\(二\)解决

7. 数据库和 Redis 的数据一致性如何保证?下方\(三\)解决



### 因此，新的方案将集中考虑和解决这些问题



## 用户并发抢券与异步落库

### 最终方案：生产者确认 \+ 消息/队列持久化 \+ 失败重试 \+ Redis可回滚 \+ 数据库UNIQUE联合字段 \+ 对账兜底

存储：我们采用 String 结构存储库存（key 是 `seckill:stock:券id`，value 是剩余库存数），然后用 Set 结构记录用户下单保证一人一单（key 是 `seckill:order:券id`，member 是 userId）。用户并发抢券时我们采用 Lua 脚本原子地做【校验一人一单 \+ 预扣库存 \+ 记录标记】，Lua 脚本抢券成功了就发消息到 RabbitMQ 异步落库，同时发一条延迟消息 5 分钟后让订单过期。



```Plain Text
① Redis Lua 抗并发（预扣库存 + 一人一单去重，只存 userId）
        ↓
② 发 MQ（confirm + 消息/队列持久化 + 失败重试）
   ├─ ack → 返回"处理中"
   └─ 失败/超时 → 回滚 Redis（Lua 原子 + 幂等）→ 返回下单失败
        ↓
③消费者落库（一个事务内两道防线）
   ├─ ① 扣 DB 库存：UPDATE ... WHERE stock > 0（乐观锁）
   │     失败 = 超卖 → 回滚 Redis + 告警
   ├─ ② 建订单：INSERT（UNIQUE(user_id, voucher_id)）
   │     冲突 = 重复 → 告警 + 复用旧单返回(旧单未过期)
   ├─ 成功 → ack → SSE 通知前端（订单=待支付）
   │      └─ 再发【延迟消息】（5 分钟后超时检查）
   └─ 失败重试 → 有限次 → 死信 + 回滚 Redis + 告警
        ↓
④ 延迟消费者（5 分钟后）
   ├─ 已支付 → 忽略
   └─ 未支付 → 取消订单 + 释放 DB/Redis 库存 + 删一人一单标记
        ↓
⑤ 定期对账（兜底）+ 定期以 DB 重建 Redis（Rabbitmq没消息时）
```

在订单成功落库之前，订单状态必须是处理中，不能lua扣减\+消息队列返回ack时就返回待支付，要为消息队列的不确定性兜底。

## 新旧方案对比

### 原有方案 vs 最终优化方案

|维度|原有方案|最终方案|
|---|---|---|
|MQ 可靠性|裸 convertAndSend 无 confirm|confirm \+ 持久化 \+ 失败重试 \+ 死信队列 \+ 对账兜底|
|消费失败|只 log 不 ack/nack，消息卡死|有限重试 \+ 死信 \+ 回滚 Redis|
|重复下单|无 DB 唯一索引兜底<br>|UNIQUE\(user\_id, voucher\_id\)|
|库存一致性|Redis/DB 双写无协调<br>|落库乐观锁防超卖 \+ 对账<br>|

### \(一\)\. 消息可靠性问题（MQ 宕机 / 丢消息 / 延迟 / 没有回复）



### 1\.1 宕机、消息丢失解决方案：持久化 \+ 对账兜底

宕机、消息丢失的解决就是开启消息持久化和队列持久化，让消息和队列在重启或者宕机后也不会丢失。

### 1\.2 消息延迟解决方案：处理中状态 \+ SSE 通知 \+ 对账

异步落库天然就具有延迟的特性，所以订单状态就需要"处理中"而不是"下单成功"，订单状态机的设计应该是 处理中 → 待支付 → 已支付/已取消/抢票失败，只有消费者处理时订单落库成功才可以返回下单成功，前端通过 SSE 长连接实时接收"落库完成"通知，落库完成了才会显示落库完成。



### 1\.3 消息队列没有回复



### 解决方案：发消息失败/超时则Redis回滚，返回抢单失败让用户重试

发消息时开启生产者确认机制。如果收不到 ack、或者等待超时，说明消息没可靠送达，此时直接回滚Redis（Lua 原子删一人一单标记 \+ 库存\+1），返回失败让用户重试。我们通过回滚机制保证如果消息队列出问题，还能让redis回退，相当于事务的回滚。



### 疑问：那如果实际上消息进消息队列了，但是后端返回失败redis回滚了，那不就数据不一致了么？

返回不是只有 ack（成功）和 nack（失败），还有第三种——超时。超时意味着你根本不知道消息到底进没进队列。这时候如果回滚 Redis，而消息其实进了队列，消费者落库，此时就会出现数据库有订单且扣了库存，但是redis显示没有订单且库存数比数据库多，那怎么办？

### 疑问解答：数据库也使用乐观锁防超卖 \+ 落库时冲突则日志告警 \+ 定时对账保证redis和数据库信息一致

而且用户见到的其实是订单下单失败，订单状态也是从处理中变为下单失败，这是可以接受的（而不是显示下单成功待支付结果失败，或者订单已支付时失败）



### \(二\)\. 落库失败与幂等问题,修改余票和座位状态失败处理,失败重试造成的多次操作的幂等性

这里是前面消息队列各种不稳定，延迟，不回复导致Redis回滚等等问题的兜底。

### 处理方法：消费者确认机制 \+ 落库语句幂等性保证

开启消费者确认机制，只有修改成功才可以返回Ack，不允许订单没有延迟但修改余票和座位状态失败的情况出现。同时消费者落库时，在一个事务里做两道防线：



- 第一道：乐观锁防超卖。`UPDATE tb_seckill_voucher SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0`。如果update方法返回`0`（表明影响0行），那就说明Redis那边库存比数据库多，Redis实际上超卖了，直接回滚Redis \+ 告警。

- 第二道：唯一索引防重复。`tb_voucher_order` 加 `UNIQUE(user_id, voucher_id)`。重复消息、或用户重试导致重复落库时，插入会抛唯一约束冲突，捕获后告警 \+ 复用旧单返回。

这样就算Redis和数据库数据不一致造成的额外下单，或者消息队列没有回应导致Redis回滚但是实际收到消息（一人一单标记消失后用户又可下单，此时一个用户就能发两条落库消息），这些情况下仍然有数据库的唯一索引防重复下单\+乐观锁防超卖。此时数据库返回错误，处理这些错误即可。

### 两道防线错误情况下的处理方法：

扣库存失败 = 意味着超卖 → 回滚 Redis \+ 日志告警

唯一索引冲突 = 意味着重复下单 → 日志告警 \+ 复用旧单返回（订单若未超时过期）\+ DB重建Redis缓存信息

只有落库成功订单状态才能变成待支付，这样抢票失败或者lua成功但落库失败或者lua成功但消息队列无反应或者消息队列中间丢消息显示的都是抢票失败，用户接受度更高





### 三\. Redis与DB一致性问题（Redis 预扣 vs DB 最终库存）



### 最终方案：以 DB 为准 \+ 定期对账 \+ 告警 \+ 重建

Redis 预扣允许和 DB 短暂不一致，最终靠对账任务以 DB 为准补平。活动开始后我们每2个小时执行一次对账任务，如果对账发现异常则根据数据库重建缓存。

### 疑点：对账的时候，正好有订单在消息队列里没落库怎么办？

### 疑点解答：只在消息队列中没有消息的时候重建

若有消息正好卡在代码里尚未产生消息，那确实很巧了，只能说等待下次对账修复掉，我们至少有数据库的防重复和防超卖兜底。
